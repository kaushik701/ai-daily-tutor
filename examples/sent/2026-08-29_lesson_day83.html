Day 83: Vector DB Choices in Production
TL;DR
A quick guide to picking between pgvector, Pinecone, Weaviate, and Qdrant for production vector search.

In plain English

Vector databases store high‑dimensional embeddings so you can retrieve similar items quickly. In production you must balance three forces: operational overhead (self‑hosted vs managed), scaling behavior (how many vectors, query latency, concurrent users), and ecosystem fit (SQL integration, API style, extra features like metadata filtering).\n\npgvector is a Postgres extension, so if your stack already runs PostgreSQL you get vector search with zero new infra, but you inherit Postgres scaling limits. Pinecone is a fully managed SaaS that auto‑scales, offers guaranteed SLAs, and hides replication details, at the cost of vendor lock‑in and higher per‑query price. Weaviate is open‑source with GraphQL/REST APIs and built‑in modules (e.g., hybrid search, transformers), letting you run on‑prem or in the cloud while still getting richer query primitives. Qdrant, written in Rust, excels at payload filtering and offers both self‑hosted and managed options; its API is simple and it is known for low latency on large collections.

Think of it this way

Choosing a vector store is like picking a kitchen appliance: pgvector is the built‑in stove you already have—reliable but limited in size; Pinecone is a high‑end countertop espresso machine—plug‑and‑play with consistent output but you’re tied to the brand; Weaviate is a multi‑function food processor that can blend, chop, and knead, giving you many modes in one box; Qdrant is a precision sous‑vide device that maintains exact temperature (latency) and lets you add custom ingredients (metadata filters) while you control the whole setup.

In code

import psycopg2, numpy as np\n\nconn = psycopg2.connect("host=localhost dbname=mydb user=me password=secret")\ncur = conn.cursor()\n# create table with pgvector column\ncur.execute("CREATE TABLE IF NOT EXISTS docs (id SERIAL PRIMARY KEY, content TEXT, embed VECTOR(1536));")\n\nvec = np.random.rand(1536).astype(np.float32).tolist()\ncur.execute("INSERT INTO docs (content, embed) VALUES (%s, %s)", ("sample text", vec))\nconn.commit()\n# simple similarity search\ncur.execute("SELECT id, content FROM docs ORDER BY embed <-> %s LIMIT 5;", (vec,))\nprint(cur.fetchall())\ncur.close(); conn.close()
The snippet creates a pgvector column, inserts a random embedding, and runs a nearest‑neighbor query using the <-> operator.

Why it matters for AI Eng interviews

Retrieval‑augmented generation (RAG) and autonomous agents rely on fast, reliable vector lookup; the choice of store directly impacts latency budgets, cost, and observability pipelines that monitor query times and error rates. Fine‑tuning loops often re‑embed data, so a store that supports bulk upserts and versioned payloads eases the pipeline. Production teams look for clear SLAs, easy scaling (MCP – model‑compute‑pipeline integration), and built‑in metrics to satisfy engineering and DevOps requirements, making the architecture decision a key interview talking point.
One thing to remember
Match the DB’s operational model and feature set to your product’s latency, scale, and ecosystem needs.
